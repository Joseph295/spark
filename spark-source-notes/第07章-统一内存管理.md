# 第 7 章 — 统一内存管理:一道会移动的墙

> 对照源码:`core/.../memory/UnifiedMemoryManager.scala`、`ExecutionMemoryPool.scala`、`core/src/main/java/org/apache/spark/memory/TaskMemoryManager.java`(apache/spark master)

---

## 一、宏观:两种内存的世仇,与血缘给出的解法

Spark 用内存干两件互相争抢的事:
- **Execution(执行内存)**:shuffle 排序缓冲、聚合 hash 表、join 哈希表——临时、per-task,用完即弃(第6章 ExternalSorter 要的就是它)。
- **Storage(存储内存)**:cache/persist 的 RDD 块、broadcast——长期、跨 task 存活。

1.6 前**静态切分**(shuffle/storage.memoryFraction 一道死墙):重 cache 作业饿死 execution,重 shuffle 作业浪费 storage。没有比例能适配所有作业。

1.6 后 UnifiedMemoryManager:一个池两个区,**边界可移动**,但**借用不对称**:
> Execution 可【抢占/驱逐】Storage;Storage 只能【借用】Execution 的空闲,不能抢占。

> ★ 不对称=血缘的馈赠(第0章)。Storage 存 cache 块,丢了能靠血缘重算 → 安全驱逐;Execution 是正在跑的 task 的中间状态,抢走 task 当场崩、无从重算。"能不能被牺牲"取决于"丢了能不能廉价恢复"=RDD 容错核心。内存设计根扎在三章前的容错哲学。

抢占 storage 仍不够时,execution 最后一招:逼其他 consumer **spill 到磁盘**(第6章 ExternalSorter spill 在此触发)。

## 二、细节

### 2.1 内存布局(`UnifiedMemoryManager.scala` 200–243)
```scala
200  RESERVED_SYSTEM_MEMORY_BYTES = 300MB          // 雷打不动留给系统
240  usableMemory = systemMemory - reserved        // 堆 - 300MB
242  统一池 = usableMemory * MEMORY_FRACTION(0.6)
207  onHeapStorageRegionSize = maxMemory * MEMORY_STORAGE_FRACTION(0.5)  // storage 受保护底线
```
例:1GB 堆 → -300MB=724MB → ×0.6=434MB 统一池;×0.5=217MB storage 区。
**0.5 不是死墙,是"借用分界线"=storage 受保护、不可被抢占的底线。** 用量在线内 execution 抢不走,超线借来的随时要回。
> ★ 300MB reserved + 219 行 minSystemMemory=reserved×1.5 fail-fast(堆太小直接报 INVALID_EXECUTOR_MEMORY,SPARK-12759)。启动即清晰报错,非运行时神秘 OOM(同第5章 maxResultSize 价值观)。

### 2.2 Execution 借 Storage:可抢占(86–150)
```scala
112  maybeGrowExecutionPool(extraNeeded):
118    reclaimable = max(storagePool.memoryFree,            // storage 空闲的
119                      storagePool.poolSize - storageRegionSize)  // 或 storage 借超 region 线的部分
123    spaceToReclaim = storagePool.freeSpaceToShrinkPool(...)  // ← 必要时【驱逐缓存块】!
125    storagePool.decrementPoolSize(spaceToReclaim)         // storage 缩
126    executionPool.incrementPoolSize(spaceToReclaim)       // execution 涨 → 墙移动
144  computeMaxExecutionPoolSize = maxMemory - min(storage.memoryUsed, storageRegionSize)
```
> ★ SPARK-12155(131-137,144-146):算 task 可用上限必须把"可驱逐 storage"算进去,否则 task 误以为没内存而阻塞,其实踢几个缓存块就够。故减的是 min(storage用量, region线),region 线以上全算 execution 够得着。

### 2.3 Storage 借 Execution:只能借空闲(152–184)
```scala
175  if (numBytes > storagePool.memoryFree)
178    borrowed = min(executionPool.memoryFree, numBytes - storagePool.memoryFree)  // ← 只取 execution【空闲】!
180    executionPool.decrementPoolSize(borrowed); storagePool.incrementPoolSize(borrowed)
168  if (numBytes > maxMemory) return false   // 块比整池还大,fail-fast 拒
```
对比 2.2:execution 借 storage 会 freeSpaceToShrinkPool(驱逐);storage 借 execution 死卡 memoryFree(在用的一字节都动不了)。这就是"storage 不能抢占 execution"的代码体现。借完不够则缓存请求被拒(块存磁盘)。

### 2.4 Execution 内 task 公平:1/N 与 1/2N(`ExecutionMemoryPool.scala` 92–149)
execution 池被一 executor 上并发 N 个 task 共享(第5章线程池)。防贪心 task 吃光:
```scala
113  while (true) {
114    numActiveTasks = memoryForTask.keys.size       // N 动态变化
120    maybeGrowPool(numBytes - memoryFree)           // 每轮先试抢 storage
128    maxMemoryPerTask = maxPoolSize / numActiveTasks    // 上限 池/N
129    minMemoryPerTask = poolSize / (2*numActiveTasks)   // 下限 池/2N
139    if (toGrant < numBytes && curMem+toGrant < minMemoryPerTask) lock.wait()  // 连1/2N都给不了→阻塞
143    else { memoryForTask(taskAttemptId) += toGrant; return toGrant }
```
规则:每 task ≤ 池/N(公平),≥ 池/2N 才放行否则 wait() 阻塞等唤醒。N 动态(task 启停),故 while 循环重算。104-106 task 注册/结束时 notifyAll。
> ★ 第5章伏笔收线:Task.run 的 finally `memoryManager.notifyAll()` 唤醒的就是 142 行这些 wait() 等内存的 task。task 释放内存→notifyAll→阻塞 task 醒→重算 1/N 份额→继续。Spark 内存"并发共享又不死锁饿死"的关键。
> ★ 1/2N 下限防活锁:无下限则老 task 占满、新 task 1/N 份额被占却忙等永不阻塞。有"≥1/2N 才放行否则阻塞"保证每 task 要么推进要么干净让出 CPU。

### 2.5 最后手段:强制 spill(`TaskMemoryManager.java` 159–233)
一个 task 内多个吃内存者(ExternalSorter、join 的 BytesToBytesMap)统称 **MemoryConsumer**,由 TaskMemoryManager 统管。抢 storage 仍不够 → 逼 consumer 吐磁盘:
```java
168   got = memoryManager.acquireExecutionMemory(required, ...)   // 先正常申请(含抢storage)
172   if (got < required) {                                       // 还不够→逼别人spill
192     TreeMap<Long, List<MemoryConsumer>> sortedConsumers      // 按内存用量排序
195       long key = c == requestingConsumer ? 0 : c.getUsed()   // 申请者记0→最后才spill自己
205     currentEntry = sortedConsumers.ceilingEntry(required-got) // 选"刚好够还的最小consumer"
207     if (null) currentEntry = lastEntry()                      // 没有就选最大
211     got += trySpillAndAcquire(...) → consumer.spill()[261]    // 第6章 ExternalSorter spill 在此
```
启发式(184-187):选"内存 ≥ 还差量的最小 consumer",平衡①少spill次数(防小文件多)②别spill过头(很多consumer一spill吐一堆)。
> ★ 两级内存管理:UnifiedMemoryManager(跨task,execution/storage宏观借用驱逐) + TaskMemoryManager(task内,多consumer微观分配与强制spill)。MemoryConsumer.spill() 是接口,任何用执行内存的组件(排序/聚合/join)实现它。**正是这套机制让 Spark 处理超内存数据不OOM**——与 groupByKey(CompactBuffer 非 MemoryConsumer、不 spill、会 OOM)的根本区别。

## 三、Trick 与 Bug
**① 不对称借用是核心(2.2 vs 2.3)。** execution 驱逐 storage(可血缘重算),storage 只借 execution 空闲(在用的丢了task崩)。根扎第0章容错。
**② 布局(200-243)。** (堆-300MB)×0.6=池;×0.5=storage受保护底线非死墙。300MB+1.5×fail-fast 保护小堆。
**③ SPARK-12155(144-146)。** 算上限须含可驱逐 storage,否则 task 误阻塞。
**④ 1/N公平+1/2N下限+wait/notifyAll(92-149)。** 防贪心防饥饿;与第5章 finally notifyAll 收线。
**⑤ spill 选择启发式(184-215)。** ceilingEntry 选"≥还差量的最小consumer";申请者记0最后spill。
**⑥ 两级管理+MemoryConsumer.spill()。** 让 Spark 处理超内存数据(vs groupByKey 会 OOM)。

## 四、本章总纲
```
世仇: Execution(临时per-task) vs Storage(长期跨task)
  1.6前 静态死墙→总有作业吃亏; 1.6后 一池两区边界可移+【不对称借用】

布局[200-243]: (堆-300MB)×0.6=池; ×0.5=storage受保护底线(非死墙); 300MB+1.5×fail-fast保护小堆
Execution借Storage[86-150]: maybeGrowExecutionPool【驱逐缓存块】(可血缘重算)→移墙; computeMax须算可驱逐storage(SPARK-12155)
Storage借Execution[152-184]: 只借 executionPool.memoryFree空闲,不抢占(在用的丢→task崩)
Execution内task公平[92-149]: ≤池/N防贪心, ≥池/2N才放行否则wait()防饥饿; N动态循环重算
  释放notifyAll ←→ 第5章 Task.run finally 收线
强制spill[TaskMemoryManager 159-233]: 抢storage不够→逼MemoryConsumer.spill()吐磁盘(第6章ExternalSorter)
  启发式 ceilingEntry选"≥还差量的最小consumer"; 申请者记0最后spill
  两级 UnifiedMemoryManager(跨task)+TaskMemoryManager(task内) → 处理超内存数据(vs groupByKey OOM)
```
