# 第 13 章 — 部署:Executor 从哪来,以及按需伸缩

> 对照源码:`core/.../ExecutorAllocationManager.scala`、`core/.../scheduler/cluster/*SchedulerBackend`、`resource-managers/{yarn,kubernetes}/`(apache/spark master)

---

## 一、宏观

前十二章默认"executor 已存在"。但 executor 进程谁/在哪/怎么启动?=集群管理器的职责。
Spark 支持 Standalone/YARN/Kubernetes(+local,+已废弃 Mesos),靠第4章接缝统一:
> **SchedulerBackend 是引擎与集群管理器之间唯一的接缝。** 每种集群管理器提供自己的 SchedulerBackend 子类+"如何启动 executor";其上一切(Task/DAG/shuffle/内存/SQL)**完全不知道自己跑在 YARN 还是 K8s**。

> ★ 第0-12章源码几乎找不到 "YARN"/"Kubernetes"。核心引擎集群管理器无关,部署层只是可插拔薄底座。故同一套引擎在 local/Standalone/YARN/K8s 用完全相同执行逻辑——换部署只换最底层 backend,上面十二章一字不变。

## 二、细节

### 2.1 接缝:SchedulerBackend 三子类
CoarseGrainedSchedulerBackend(第4章 makeOffers/launchTasks 基类)是公共基础。每种集群管理器只补"怎么申请/启动 executor":
- StandaloneSchedulerBackend
- YarnSchedulerBackend(YarnCluster/YarnClient)
- KubernetesClusterSchedulerBackend
差异只在 executor 申请与启动,resourceOffers/launchTasks(第4章)完全共享。

### 2.2 三种部署(对照 Hadoop 心智)
**① Standalone:** Spark 自带。Master(集群RM)+每节点 Worker 守护进程。应用向 Master 注册→Master 让 Worker 启动 CoarseGrainedExecutorBackend。Master 管应用间调度(FIFO+spread-out)。简单原生无外部依赖。
**② YARN:AM 模式(Hadoop 锚点)。**
- **client 模式**: driver 跑在提交进程(你的 spark-submit JVM),YARN 上轻量 AM(ExecutorLauncher)只申请 container 启动 executor。适合交互式(driver 本地能看输出)。
- **cluster 模式**: driver 跑在集群 AM container 内。AM=ApplicationMaster,既运行 driver 又向 ResourceManager 申请 executor container——同 MR AM 申请 map/reduce container,区别仅 Spark 申请长驻 executor 而非用完即弃的 task container。
> ★ client vs cluster 唯一本质区别=**driver 进程在哪**。client driver 在提交端(看日志方便);cluster driver 在集群 AM 容器(离 executor 近/容错好/生产)。第1章"SparkContext 在你 main 里 new"——client 在本地进程,cluster 在 AM 容器。部署模式决定 driver 大脑的物理位置,非执行逻辑。
**③ Kubernetes:** 无独立 RM。driver 本身是 pod,直接和 K8s API Server 对话创建 executor pod。ExecutorPodsAllocator 管 pod 生命周期。无需 Hadoop/YARN,复用 K8s 调度/隔离/弹性。Spark 上云主流。

### 2.3 动态资源分配 ExecutorAllocationManager(反馈控制器)
问题: executor 太少 task 排队;太多浪费(云上为闲置付费)。
**信号=有多少 task 在等。目标(297-318):**
```scala
302  numRunningOrPendingTasks = pendingTask + pendingSpeculative + running
304  tasksPerExecutor = rp.maxTasksPerExecutor(conf)
307  maxNeeded = ceil(numRunningOrPendingTasks * executorAllocationRatio / tasksPerExecutor)
```
即 ⌈(待处理+推测+运行中 task)/每executor并行task数⌉="够并行跑完当前所有task的executor数"。
**控制循环 updateAndSyncNumExecutorsTarget(373-400):**
```scala
384  if (maxNeeded < targetExecs) decrementExecutorsFromTarget(...)  // 需求<目标→调低目标(但不杀!)
394  else if (now >= addTime) addExecutorsToTarget(...)              // 积压持续够久→加
```
- 扩容: 积压>schedulerBacklogTimeout(默认1s)开始加; 持续积压(sustainedSchedulerBacklogTimeout)每轮翻倍(1→2→4)指数爬坡,快速响应大积压。
- 缩容: 空闲>executorIdleTimeout(默认60s)移除; **例外**: 持缓存块的用 cachedExecutorIdleTimeout(默认∞)不轻易杀(否则丢缓存/重算)。
> ★ "目标"与"杀死"解耦(388-392): 需求降只**被动调低申请**(不要新的),不主动杀正用的;杀只由空闲超时独立触发。理由: executor 可能本就要挂(故障/抢占),没必要急替补;在跑task的不能半路杀。**控制论的滞后(hysteresis):被动减请求+只在持续空闲才释放,避免负载抖动反复增删(thrashing)。** 同第4章延迟调度等3s、第3章 FetchFailed 攒200ms、第10章 AQE 等shuffle完成——"用延迟/滞后避免过度反应"在资源伸缩的体现。
> ★ cachedExecutorIdleTimeout 是第12章回响: cache 让 executor 变"黏"(不只是计算单元,还是数据持有者,杀它代价大)。引出动态分配最大历史难题——**shuffle 文件问题**: executor 被杀其 shuffle 输出(第6章)消失→FetchFailed(第3章)→重算。故早期动态分配必须配**外部 shuffle 服务**(每节点独立守护进程托管 shuffle 文件,独立于 executor 存活)才能安全撤 executor。reliableShuffleStorage(109)/push-based shuffle 缓解此问题。

**落地:** doUpdateRequest(398)→ client.requestTotalExecutors → client=SchedulerBackend(接缝)→ 翻译成具体动作:YARN申container/K8s建pod/Standalone请Master。统一的"要N个executor"经接缝分发三种集群管理器。

## 三、Trick 与 Bug
**① SchedulerBackend 接缝=核心引擎集群管理器无关(2.1)。** 换部署只换底层 backend。
**② YARN client vs cluster=driver 在哪(2.2)。** client 提交端(交互);cluster 集群 AM 容器(生产)。
**③ 目标公式(297-308)。** ⌈(pending+speculative+running)/tasksPerExecutor⌉。
**④ 指数扩容。** 持续积压每轮翻倍 1→2→4。
**⑤ 目标与杀死解耦+滞后(388-392)。** 需求降被动减请求,杀只由空闲超时;防 thrashing。同第3/4/10章。
**⑥ cachedExecutorIdleTimeout(97-99)。** 不轻易杀持缓存 executor(第12章回响)。
**⑦ 外部 shuffle 服务。** executor 杀→shuffle 丢→FetchFailed→重算; 故需独立托管 shuffle 输出。
